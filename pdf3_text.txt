  Reason: Full multi-specialty coverage (internal medicine, cardiology, oncology,

3. Hallucination Rate — Four-Part Evaluation Protocol (Resolved)
================================================================================

The 2025 JAMIA review of RAG-in-clinical-LLM literature is explicit: "Studies
increasingly fine-tune LLMs to assess the relevance of retrieved evidence, verify
generated statements are evidence-based, and confirm the response actually
addresses the clinical question — there remains real room for improvement in how
rigorously this is evaluated."

Your paper uses a four-part protocol (addresses the standardization gap directly):

  1. Answer Accuracy (vs. MedQA/PubMedQA ground truth)
     → Top-1 accuracy on MCQ; reported per baseline and per θ value

  2. Groundedness (RAGAS Faithfulness + custom NLI check)
     → Does every claim in the answer trace back to a retrieved passage?
     → Measured via DeBERTa-v3-MNLI entailment (entailment prob > 0.7)
     → Spot-validated by human review on a 50-sample subset
     → RAGAS Faithfulness score for cross-paper comparability

  3. Retrieval Precision (RAGAS Context Precision + Context Recall)
     → Are the top-k retrieved chunks actually relevant?
     → Measured via RAGAS judge (HF Inference API, zero local VRAM)

  4. Abstention Behavior (novel contribution — no off-the-shelf tool)
     → Does the system correctly say "insufficient evidence" when the corpus
       doesn't cover the question?
     → Sweep θ ∈ {0.5, 0.6, 0.7, 0.75, 0.8, 0.85, 0.9}
     → Record (threshold, accuracy, abstention_rate, hallucination_rate)
     → Plot Pareto curve → Figure 1 in the IEEE paper

This four-part protocol is STRONGER and more publishable than accuracy alone.
Build it into the evaluation harness (src/experiments/ragas_eval.py) in Sprint 1,
not as a week-15 afterthought.

4. Preprocessing & Chunking (Resolved — mirrors pdf2_text.txt §3)
================================================================================

Chunk size: 512 tokens per chunk, 100-token overlap (in configs/seeds.yaml).
  Start here; validate against your retrieval-precision metric before changing.

Chunk by structure first (guideline docs have clear section headers):
  "Diagnosis" / "First-line treatment" / "Contraindications" / "Dosing"
  → Preserve section type as metadata on each chunk

Metadata on every chunk:
  source (str): guideline name (e.g., "WHO Infectious Disease Guideline 2023")
  specialty (str): "infectious_disease"
  section_type (str): "diagnosis" | "treatment" | "contraindication" | ...
  publication_date (str): year
  chunk_id (uuid): for citation display

Keep source citations attached to every chunk:
  → Enables "Grounded in [WHO ID Guideline 2023, §Treatment]" in answers
  → Both a safety feature and a strong demo moment for reviewers

De-duplicate across corpora if you combine epfl-llm + MedWiki + ClinicalCorp:
  → Overlapping content will skew retrieval toward duplicated topics

Implementation: src/data/guidelines_loader.py (Sprint 1, Task 1.1)

  This fits cleanly in ChromaDB's local scale capacity (~2–5M vectors).

6. Data Governance (state this explicitly in your proposal and paper)
================================================================================

Every source used is either:
  • Open-access/de-identified (MultiCaRe — PubMed Central articles)
  • Formal public guideline documents (WHO/NICE/CDC, epfl-llm/guidelines corpus)
  • Standard research benchmarks (MedQA, PubMedQA — designed for model eval)

NO real patient-identifiable data is used anywhere in this project.

This preempts the most common review-panel question for any "clinical" capstone.
State it plainly in:
  • The capstone proposal (Section "Realistic Constraints")
  • The paper (Methods section, Data paragraph, first sentence)
  • The demo / README disclaimer
